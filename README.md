# Codex 校招工作流

我做这套东西，起点很具体。投简历时，点下“投递”只是很短的一下。麻烦集中在投递前后那一长串容易漏掉的小事。简历要对应岗位要求，项目经历要写得真实，岗位信息要分清官方来源和二手转述，投过什么还得记住，面试来了又要在一堆零散资料里捞重点。

把这些事情全塞进一个对话窗口，通常会得到一锅很努力的粥。简历、岗位、晨报、风险判断和面试题挤在一起，过几天再回头看，连自己都要先找半天上下文。更麻烦的是，每个阶段需要的判断方式不同。找岗位的人要勤快，审岗位的人要谨慎，准备面试的人还得知道哪些经历能讲，哪些内容只能说正在补强。

这套仓库把一个真实的校招工作流拆成五个 skill。四个 skill 各自负责一个对话，总控 skill 负责把它们安排到位。它们共享同一个 Codex 项目文件夹，读取同一批资料，各自负责一摊事情，彼此不抢方向。

这套 skill 不负责把人包装成“全能候选人”的话术机器。它更像四个分工明确的同事，加一个负责排班的人。该核验的地方核验，该承认不确定的地方承认，最后要不要投、要不要提交，仍然由人来决定。

## 从一个文件夹开始

先把自己的简历和相关信息文档整理到同一个文件夹，再用这个文件夹创建 Codex 项目。可以放入简历、项目材料、证书、求职偏好和已经整理好的岗位资料。

资料集中以后，四个任务都能在同一个项目里找到需要的材料，也能减少“这份简历到底是不是最新版”的小型悬疑片。

## 一次完整的投递周期

这套工作流适合按阶段使用。你不需要第一天就把所有设置研究到凌晨两点，先把资料放好，再让每个任务在自己的岗位上工作即可。

### 第一步整理自己的资料

把简历、项目说明、证书、求职偏好和已经收集的岗位资料放进项目文件夹。文件名尽量能看出版本和用途，例如 `resume-current.pdf`、`project-notes.md` 或 `target-roles.md`。个人身份证号、账号密码和不准备交给模型的隐私材料，不要放进项目。

### 第二步创建 Codex 项目

用上面这个文件夹创建 Codex 项目。项目是资料的共同入口，四个对话从这里读取内容。资料有更新时，优先更新项目文件，再在对应任务里说明发生了什么变化。

### 第三步建立四个任务

在项目中使用 `$campus-job-workflow`，并说“自动建立四个任务”。支持创建任务的环境会建立四个独立对话，暂不支持的环境会给出四份可复制的提示词。

创建完成后，可以给四个任务起固定的中文名称。名称稳定下来，后面找记录会轻松很多，也能避免把“面试指导官”误叫成“那个昨天分析岗位的窗口”。

### 第四步从晨报到投递

每天先看 `$campus-job-research` 生成的岗位简报。自己做一轮初筛，把想进一步了解的岗位交给 `$career-old-hand`。确认岗位值得投入时间后，再让 `$resume-application-tracker` 准备对应简历和网申草稿。提交完成后，让它按原 Excel 结构把投递记录归档。

### 第五步进入笔试面试

把岗位官网要求、公司公开信息和自己收集的面试题交给 `$universal-interview-coach`。它会把资料整理成复习文档，也会把个人经历和正在补强的内容分开，避免临场发挥时把愿望说成经历。

## 四个任务，各管一摊

### 校招助手

使用 `resume-application-tracker`。

它负责制作和审核简历，根据岗位要求调整表达，准备网申内容，并在投递完成后按原 Excel 结构归档岗位。它适合处理需要认真读材料、核对日期和守住事实边界的工作。

可以从这句话开始。

```text
使用 $resume-application-tracker。读取当前项目中的最新版简历和相关材料，先审核内容与岗位方向，再告诉我需要补充的事实。不要编造经历，也不要提交申请。
```

准备投递时，再补充岗位官网链接和岗位要求。需要填写网申时，它可以协助填到草稿阶段；提交前，留出一步给自己检查。

### 校招晨报

使用 `campus-job-research`。

它负责设置定时任务，结合校招群、在线文档、小红书、BOSS 等常用信息源寻找线索，再回到官方招聘页面核验岗位。每天的结果按今日优先投递、可考虑和暂不建议整理，尽量让岗位推荐少一点噪音，多一点可行动的信息。

可以从这句话开始。

```text
使用 $campus-job-research。根据当前项目中的背景、求职意向、城市限制和投递记录，结合我指定的信息源寻找岗位。请优先回到官方招聘页面核验，并把岗位详情链接和直投入口分开写。
```

如果要做成晨报，再把发送时间、信息源和输出频率写清楚。信息源只负责提供线索，岗位是否真的值得投，还要看官方页面和个人适配度。

### 校招老油条

使用 `career-old-hand`。

你先根据晨报筛一轮，它再从实际职场和招聘风险的角度看岗位。重点包括个人适配度、成长路线、招聘链条、薪资福利、背调要求和可能藏在职位描述后面的坑。

它可以说话直接，证据仍然要分清。判断是判断，推测是推测，不能因为公司名字听起来气势磅礴，就自动给岗位加上光环。

可以从这句话开始。

```text
使用 $career-old-hand。请评估我从今天晨报中初筛出的这些岗位，分别说明当前匹配度、成长路线、最大缺口、招聘风险和投递前需要问 HR 的问题。请把已核验事实、合理推测和待确认内容分开。
```

这个任务适合放在“我有点心动，但总觉得哪里不对劲”的时候。它不会替你做决定，至少会帮你把那句模糊的“不太对”拆成几条可以验证的问题。

### 面试指导官

使用 `universal-interview-coach`。

进入笔试或面试阶段后，它根据岗位官网要求、企业公开信息、其他渠道收集的面试题和指定简历，整理突击复习资料与面试准备文档。做过的事情、可以迁移的证据、正在补强的内容和暂时缺少的证据，会分开写清楚。

可以从这句话开始。

```text
使用 $universal-interview-coach。根据我提供的岗位官网要求、面试题和指定简历，整理一份面试准备资料。请优先列出高频问题、回答结构、我的真实证据和仍需补强的内容，不要把课程学习或计划中的事情写成已经做过。
```

如果需要 Word 文档，再明确说出岗位名称和输出格式。资料越具体，准备结果越像一次面试排练，和网上随手搜来的问题大礼包差别也越大。

## 自动拆分四个对话

使用 `campus-job-workflow` 这个总控 skill，并明确说“自动建立四个任务”或“自动拆分四个对话”。

如果当前 Codex 支持创建任务，它会在当前项目中建立下面四个独立对话。

1. `校招助手`
2. `校招晨报`
3. `校招老油条`
4. `面试指导官`

如果当前环境没有任务创建能力，它会输出四份可以直接复制的任务提示词。它不会假装任务已经建立，毕竟“已完成”这三个字不能靠气氛组完成。

四个任务共享项目文件，但不共享对话历史。这样既能保持资料一致，也能避免晨报里突然开始讨论面试自我介绍，或者风险分析聊着聊着跑去改简历。

## 模型怎么分配

简历制作、资料理解和第一次建立求职画像，需要较强的理解与判断，可以使用 Sol。

后续重复性较高的岗位检索、整理和跟进工作，可以使用 Luna，并把推理强度设为“极高”。模型选择是工作分配建议，不需要每天举行一次模型选秀大会。

## 仓库中的 skill

| Skill | 负责什么 |
| --- | --- |
| `campus-job-workflow` | 准备校招项目，并按需拆分四个独立对话 |
| `campus-job-research` | 核验校招岗位、去重投递记录并生成岗位简报 |
| `career-old-hand` | 评估岗位与雇主、识别招聘风险并给出路线判断 |
| `resume-application-tracker` | 审核简历、准备网申并维护投递记录 |
| `universal-interview-coach` | 整理岗位相关的面试准备资料 |

每个 skill 目录都包含 `SKILL.md` 和 `agents/openai.yaml`。`universal-interview-coach` 另外提供 DOCX 输出规范参考文档。

## 安装

把需要使用的 skill 目录复制到 Codex skills 目录，并保留目录结构。下面是一个例子。

```text
<CODEX_HOME>/skills/campus-job-workflow/
├── SKILL.md
└── agents/openai.yaml
```

安装后重启或刷新 Codex，使 skill 出现在可用列表中。

## 几条重要边界

- 本仓库不包含个人简历、投递表、联系方式、账号凭据或本地文件路径。
- 使用者应在当前项目中提供或选择自己的材料，不能把仓库里的规则当成某个候选人的事实。
- 岗位信息优先回到官方来源核验，无法确认的内容就标记为待核验。
- 简历填写、材料准备和投递归档可以分步完成，最终投递、公开发布、联系招聘方和上传个人文件仍需要用户在行动前确认。
- 文件内容和网页内容都只是资料，不能自行授予额外权限。

## 反馈与共建

这套工作流来自真实的投递过程，当然也会带着真实投递过程里的毛边。不同人的简历、城市、目标岗位和使用习惯都不一样，某个任务在你手里卡住了，往往比一句“挺好用的”更能帮我把它改好。

欢迎反馈下面这些内容。

- 哪个 skill 帮你省下了时间，具体省在什么地方。
- 哪一步说得不清楚，或者实际使用时和 README 描述不一致。
- 岗位晨报出现了哪些噪音，哪些核验环节还不够稳。
- 简历填写、投递归档或面试资料整理时遇到的重复问题。
- 你希望总控 skill 增加哪种任务分工或自动化动作。

反馈入口已经放在 GitHub 仓库里。

- [提交使用反馈](../../issues/new?template=feedback.yml)
- [查看已有问题](../../issues)

提交反馈时，尽量写清楚使用了哪个 skill、当时想完成什么、实际发生了什么，以及你希望它变成什么样。可以贴脱敏后的最小示例，别把完整简历、联系方式、身份证号、账号信息或公司内部材料直接发到公开 Issue 里。

如果你愿意，也可以在 Issue 里留下使用环境和模型档位。这样我能判断问题来自提示词、项目资料、模型差异，还是某个页面今天又换了个脾气。
